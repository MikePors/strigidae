# UI guide (`internal/userinterface/...`)

Rules for the app shell, components and views. The root `CLAUDE.md` still applies.

## Bubble Tea conventions

- **No I/O in `Update` or `View`.** Network calls, file I/O, and `$EDITOR` run inside a `tea.Cmd`; results come back as messages.
- **Result messages are typed and specific**: `pullRequestsLoadedMessage{repository, pullRequests, err}` rather than a generic message. Include enough identity (repo, PR number, a request sequence number) to discard stale responses that arrive after the user has moved on.
- **GitHub access** goes only through the `github.Client` interface and domain types; never import `internal/github/network`. API errors arrive typed (`errors.Is`/`errors.As`), and the view decides how to show them.
- **Every GitHub call has a deadline.** Take the context from `userinterface.Timeouts` (`RequestContext` for small calls and writes, `LoadContext` for loads), never `context.Background()`. A write that fails with a timeout goes through `userinterface.WriteError` so the message says it may have gone through; the view then checks `userinterface.IsWriteTimeout` and runs the same reload its success runs, so a new write does the same.
- **No goroutines** outside of `tea.Cmd`s, and no shared mutable state between the model and commands.
- **Only the root model is a `tea.Model`.** In Bubble Tea v2, `tea.Model.View()` returns a `tea.View` struct; the root wraps its output in one. Screens implement our own `userinterface.View` interface (`view.go`): `Update(msg) (View, tea.Cmd)` and `Render(width, height int) string`, plus title and help bindings.
- **Navigation is message-driven.** Views are composed by the root model's **view stack**. A view opens another by building it and returning a command producing `userinterface.PushMessage{View: view}` (or `userinterface.PopMessage`); it never reaches into the stack. `cmd/strig` builds the first view.
- **Message routing.** Keys go only to the top view. Every other message (command results, ticks) goes to every view in the stack, so a view must ignore results that aren't its own (see the identity rule above).
- **Loading and lifecycle.** A view that loads data implements `userinterface.Loader`; the status bar spinner follows the top view. A view revealed by `:q` gets `userinterface.Resumer.Resumed()` and may refresh.
- **Embedded bubbles components** (viewport, list, …): drive them through their methods (`ScrollDown`, `GotoTop`, …) in response to `keys.Message`; never forward a `keys.Message` to their `Update`.
- **Text inputs capture keys.** A view with a focused text input (filter, command line, reply box) implements `userinterface.KeyCapturer`; while it captures, it receives every key raw and no global bindings or sequences fire. `esc` must always release capture, and every capturing component needs a test proving it.
- **Scrolling lists.** Any view or component with a cursor in a scrolling list uses `internal/userinterface/components/scroll.Window` and never re-implements clamping or follow logic.
- **Sizing**: views receive the space they may draw in and must not draw outside it. Handle `tea.WindowSizeMsg` everywhere.
- **Untrusted text.** Pass all GitHub/git text through `internal/userinterface/terminaltext` before it reaches the screen: `Clean` for single-line text, `CleanBlock` before markdown rendering. Test with a hostile fixture (escape sequences, C1 controls, bidi overrides, invalid UTF-8). Accepted risk, don't re-report: markdown links render as OSC 8 hyperlinks (the URL is sanitised by `CleanStyled`), so link text can differ from its target, as on github.com.
- **Styling**: no inline colours or ad-hoc `lipgloss.NewStyle()` in views or components; add a named style to `internal/userinterface/theme`.
- **Performance**: large diffs must stay smooth. Render only the visible window, and cache expensive work (syntax highlighting, markdown rendering) keyed by content and width.

## Actions that write to GitHub

The maintainer's rules for when strig asks before acting:

- Anything that publishes or changes what other people see (submitting a review, merging, editing a published comment) always asks `y/N`, and always has a command (`:approve`, `:merge`). A key may also start it, but the `y/N` still follows; no single keypress ever publishes.
- Private drafts (pending review comments, the Files "viewed" mark) are added and edited without `y/N`.
- A reaction is confirmed by choosing it (in the picker, or by naming it in `:react <name>`); no single keypress ever adds one, and it has no `y/N`.
- **Every deletion asks `y/N`**, draft or published.
- Cancelling happens only at the `y/N`. An empty body is an error, not a cancel, and nothing is written.
- Keys with a command behind them are welcome (`e` / `D` and `:edit-comment` / `:delete-comment`; `x` and `:resolve` / `:unresolve`).
- Re-read the state before asking and again after `y`; if it changed, ask again or refuse and refresh. Never write on a stale yes.
- Every workspace action that writes declares a `writeKind` and is checked by the one guard table (`views/workspace/guard.go`): ready (the pull request loaded, and the diff too unless the table says the write needs none: the Overview comment and reactions, `:discard-review`, `:edit-pull-request`, `:ready` and `:draft`), then the target, then busy (a review being submitted, a merge in progress, a comment write in flight), then the fresh check; busy is checked again after a yes or a re-read. A new write adds a kind to the table, never its own list.

## Keybindings

Vim-first. All bindings are declared with `bubbles/key` and registered through `internal/userinterface/keys`, so the help overlay (`?`) is generated from one source of truth. Views never match on raw key strings.

**Notation.** Write keys exactly as the code does, because these strings are what the code matches on:
- control keys: `ctrl+d` (never `ctrl-d`, which silently never matches)
- shifted letters: the letter itself, `G`, `R`, `N` (not `shift+g`)
- shifted punctuation: the character itself, `}` (not `shift+]`). This relies on terminals reporting the key's text, which holds while strig requests only the kitty disambiguate flag; enabling more keyboard enhancements must keep `Text` populated
- special keys: `esc`, `enter`, `tab`, `backspace`, `up`, `down`
- **multi-key sequences are space-separated**: `g g`, `z a`, `g t`. `bubbles/key` only matches single keypresses, so sequences are matched by the sequence matcher in `internal/userinterface/keys` (pending prefix shown in the status bar, ~500ms timeout). Views just declare them in their bindings; they never track key history themselves.

The help overlay may display sequences compactly (`gg`, `za`).

There is deliberately **no single-key back or quit**: `q` and `ctrl+c` are unbound. `ctrl+o` / `ctrl+i` (back / forward through views) are reserved for later, and `tab` is unbound outside the command line; terminals send the same byte for `tab` and `ctrl+i`.

**Command-line completion** (`completion.go`). While the `:` line is open, `tab` / `shift+tab` complete the word at the end of the line: the first word against the shell's commands (table order) then the top view's, which a view lists by implementing `userinterface.CommandLister` (`CommandNames()`, the names its `Command` handles; the workspace's include its plugins); after `set ` against `options.All()` and the `no` forms; after `help ` against the help topics; after `theme ` against `scheme.Names()` (the list `--list-themes` prints); after any other command the top view lists, against what it returns from the optional `userinterface.ArgumentCompleter` (`CompleteArguments(name)`: whole arguments, which may contain spaces, that the typed argument is a prefix of; the lists answer for `mark`). Nothing else is completed, and prompts (`/`) never are. Two or more matches fill in the first and show a one-line list over the bottom row of the content, drawn by the root. Any other key keeps the line and closes the list. The keys are taken by the root, so they never reach the input (no tab character) or the view. Declared in `keys.Global.Complete` for the help only.

**Counts.** Digits `1`-`9` start a count and `0` continues it (`11j`, `3]`, `42G`), capped at 9999. The sequence matcher parses it and delivers it as `keys.Message.Count` (0 means none; `Repeat()` gives at least 1). A view applies it only to `j`/`k`, `]`/`[`, `}`/`{`, `)`/`(`, `ctrl+d`/`ctrl+u`/`ctrl+f`/`ctrl+b`, `z h`/`z l`, `n`/`N` (the count-th match), and `G` (with a count: go to line N, which in a diff is the new-side line number, or the nearest shown one; row N in lists); every other key ignores it and acts once. The count clears on any other key, `esc`, and the sequence timeout. While a view captures keys, digits are plain input.

**View commands.** The table above is static. A view with commands of its own implements `userinterface.Commander` (`Command(name, args) (tea.Cmd, handled bool)`) and declares each command on its registry entry (`keys.Action.Command`); the view package exports the names (`workspace.Commands()`), `cmd/strig` collects them and passes them to the shell as `Options.ViewCommands`. The root consults only the top view, and only when the static table has no match, so a command never reaches two views the way a broadcast result would. A listed name the top view declines (or a top view that is not a Commander) gives "not available here: name"; any other name gives "not a command: name". List the view's commands in the table above.

**Plugin commands.** A configured plugin (`internal/plugins`, `docs/plugins.md`) is a command of the workspace and reaches the registry as an entry of the same shape as a built-in action: `View.entries()` (`views/workspace/plugins.go`) returns the built-in `bindings.entries()` followed by one `actionEntry` per plugin, and key dispatch, command dispatch, the guard and the notices all read that one list. A `lines` plugin is level `levelLines`, `diffVisible`, guard `usePluginLines`; a `pull-request` plugin is level `levelPullRequest`, guard `usePluginPullRequest` (the two guard kinds write nothing, so only "not loaded" blocks them, with the built-ins' notices); neither has a key. The only exceptions to the built-in shape: the entries are made per view from the `userinterface.PluginsMessage` the root sends (like `OptionsMessage`), not declared statically, so they are not in `actions()`, `ActionNames()` or `Commands()`; `cmd/strig` appends the plugin names to `Options.ViewCommands` (so other views say "not available here") and refuses, at startup, a plugin named like any name in `userinterface.CommandNames()` or the views' `Commands()`.

Runs belong to the root model, never to a view. The entry's `run` returns a command producing `userinterface.RunPluginMessage` (the request plus the pull request's `PullRequestIdentity`: repository, number, head); the root starts the run in a `tea.Cmd` with a context it owns, so closing the view does not cancel it. The result carries the same identity and is shown only if the top view is a `userinterface.PluginHost` showing the same pull request (repository and number, through `PullRequestIdentity.SamePullRequest`, which the spinner uses too; a new head does not drop it, and the request carries the head the plugin ran at); otherwise it is dropped with a log line that has no text. Effect and error text goes through `terminaltext.Clean` before the status bar. The spinner shows while a run of the top view's pull request is active (queued runs included). Quitting (`:qa`, `:q` on the root view, `QuitMessage`) cancels all runs and waits at most `Options.PluginQuitWait` (2 seconds by default) for them, using the injected `Tick`; with no run active it quits at once. Nothing arriving after quit began is applied, and no run starts then. A view that lets `:` open the command line while it captures keys (the workspace during a `V` selection, so a `lines` plugin gets the selection) implements `userinterface.CommandLineKeeper`, and only when a `lines` plugin is configured and no picker or chooser is open; during the selection the view's commands other than a `lines` plugin's (built-ins and `pull-request` plugins) are refused with `end the selection to run :<name>`, so nothing can open under a live selection; the shell's own `:q`, `:qa`, `:set` and `:theme` still run. `Model.Close` (called by `cmd/strig` after the program returns, on every path) cancels the runs, starts stopping the runner's services before waiting for runs or file saves, and waits up to the same quit wait, for exits that skip `QuitMessage` (SIGTERM, SIGINT, a failed `Run`).

**Marks.** A mark is a private note on a pull request (`internal/pullrequestmarks`, kept in `$XDG_STATE_HOME/strig/pull-request-marks.json`). The root holds them in `marksPart` (`marks.go`: the `pullrequestmarks.Marks` value, the file path, the startup read error and the save sequence) and hands it `SetMarkMessage`, `ClearMarkMessage` and the save result in one line of `Update`. Data goes down as `MarksMessage{Marks}`, sent to every view on each change and to each view as it is pushed (the root view at start); actions go up: a list's `:mark` / `:unmark` (`MarkCommand`, `UnmarkCommand`) return a command producing the set or clear message with the `MarkKey` (the host from `ClientHost(client)`, never `github.com`, then repository and number). The part applies it, shows the result, and saves: `Encode` on the update goroutine, then a `tea.Cmd` calls `pullrequestmarks.Write`. At most one save is in flight; a change meanwhile sets `pending`, and when the save's result arrives one save of the then-latest marks follows, so an older copy never lands after a newer one. A failure is a status-bar error, logged by the root; error texts never hold the mark (the root logs every error it shows). `cmd/strig` reads the file before the program starts and passes `Options.Marks` and `Options.MarksError`; after a read error the marks work for the session but are never written, so the unusable file isn't overwritten. With no `StateDirectory` they are session only. Views keep only the last `MarksMessage` and derive the MARK column (`pullrequestrows.Options.Mark`) at render; the column is shown only while a row has a mark and is the first one dropped on narrow terminals.

**Local threads.** A plugin with `show: thread` (config: `lines` plugins only) draws its question and answer as a thread that exists only in strig. The root owns the store (`localthreads.Store` from `internal/localthreads`, keyed by host, repository and pull request number, each thread holding the head it was asked on and when; the views know a thread as `userinterface.LocalThread`, an alias of `localthreads.Entry`) and tells views with `userinterface.LocalThreadsMessage`, on every change and when a view is pushed. The thread is added when `RunPluginMessage` is handled (so it shows even while the run waits) and filled when the result arrives, **whatever pull request is on top**; other effects keep the host rule above. A local thread is marked by the typed field `github.ReviewThread.Local` (`github.LocalState`), never by its identifier. The workspace keeps it out of `view.threads` (GitHub's threads: the Overview, counts, the unresolved state and every write read only that) and gives the diff pane both through `setPaneThreads`; outdated is worked out there against `diffHead`, never stored, and an outdated one has no line, like a GitHub one. **The target resolver is the one gate:** it refuses a local thread for every thread- and comment-level action (`r`, `x`, `:resolve`, `:unresolve`, `e`, `D`, `:edit-comment`, `:delete-comment`, `:react`) with `this answer is local to strig, not on GitHub: nothing to <verb>` (the verb is the entry's `words` without " it"); a new action at those levels gets this by using the resolver, and no write may take a thread from anywhere else. **Kept between runs.** The rules live in `internal/localthreads` and are unit-tested there without the model: `Store` (limits, identifiers, merge) and `Files` (what is in flight, pending, generations, unreadable files, the flush at quit). `localthreadsfile.go` is only the glue: it asks `Files` what to do and turns the answer into `tea.Cmd`s and messages. A new rule goes in the package, not in the model. The behaviour: one JSON file per pull request under `<state directory>/strig/local-threads/<host>/<owner>/<name>/<number>.json`, the state directory passed in `Options.StateDirectory`. All file I/O is in `tea.Cmd`s. A workspace sends `PullRequestOpenedMessage` when its pull request loads (a change that comes first starts the read itself and waits for it); the first one per pull request in a run reads the file (counted as an operation in flight, so nothing is written over it first) and merges it into the store (`Store.Merge`: no duplicates, identifiers renumbered on a clash and numbering continued after the largest loaded one, a waiting thread becomes `no answer: strig was closed` and is saved back). Every change writes the whole file atomically; at most one operation per pull request is in flight and a change meanwhile sets `pending`, so one write of the latest copy follows and an older copy never lands after a newer one. Each change bumps a generation and a write is skipped if a newer generation was written, so `Close` writes every changed pull request directly (it does not rely on a write command having run, and reads and merges a file never read), within the quit wait. No host, or a path part that is not a plain name, keeps nothing (logged once). A file that can't be used (unreadable, undecodable, unknown version, over 4 MiB) is logged without content and renamed to `<number>.json.unreadable` before the next write. The read command marks it (`Files.Load`, under the file mutex, off the update goroutine); nothing on the update goroutine takes that mutex. At most `DefaultLocalThreadLimit` (200) threads per pull request; the oldest by asked time goes, and so does the oldest until the encoded file is within `localthreads.MaxFileSize` (what a read accepts; `Store.Fit`, run on every change, dropping from the store too). `Close` does all its file work, mutex included, in a goroutine after cancelling the runs, so a stuck disk can't hold quit. Log lines never hold thread text. Text of the answer and the failure is the plugin's: Markdown goes through `CleanBlock`, `no answer: ...` through `Clean`.

|---|---|
| `g …` | goto: `g g` top, `g t` / `g T` next / previous tab |
| `z …` | folds (expand/collapse threads, files), horizontal scrolling (`z h` / `z l` a few columns, `z H` / `z L` half a screen, as in vim) and screen positioning: `z t` / `z z` / `z b` scroll the cursor line to the top / middle / bottom of the view without moving the cursor (lists with a cursor; they take no count, and the Overview doesn't have them yet) |

**Targets.** Thread actions (`r`, `x`, `:resolve`, `:unresolve`) use the selected Comments review thread while Comments is shown, or the diff cursor otherwise. Comment actions (`e`, `D`, `:edit-comment`, `:delete-comment`), `c`, `V`, and `m` use the diff cursor. Cursor actions require the right pane to be visible, focused or not; a narrow terminal showing Files says `focus Comments to <action>` only for thread actions targeting Comments; diff-only actions keep `focus the diff to <action>`. The workspace resolves their target in one place (`views/workspace/target.go`), with one notice per level. A comment-level target is a `commentTarget` (`views/workspace/commenttarget.go`: kind, identifier, author, reactions, the viewer's rights, pending, the review thread if any), so it does not depend on the pane that produced it. Still outside the resolver: `v` and `:copy-filename` (file level), `C` and `:copy-url` (pull request level). `:react` takes its comment context from the diff cursor or an Overview target picker. Both the target picker and the reaction menu resume the shared dispatcher with an explicit comment context, which `resolveTarget` refreshes by identifier and checks with the same target rules.

Adding a binding or command: make sure it doesn't collide with the tables above or another binding active in the same view, add it with help text and an action name, and **list every new or changed binding in the PR description** so the maintainer can approve it. Any binding an issue marks "TBD" is the maintainer's call; propose one in the PR and ask.

Action names are the stable names a config file will use for bindings. A global binding (a `key.Binding` field of `keys.Global`) is named in `Actions` in `keys/actions.go`. The workspace declares each of its actions once, in `views/workspace/registry.go`: a `keys.Action` (name, binding, `:command`) plus the target level, whether the diff pane must be on screen, the guard kind (and `overviewGuard` for description/top-level contexts), the fresh-check policy and the function that runs it. A key and its command both run the same entry through one dispatcher, in the order arguments, ready, optional comment-target picker, diff on screen for cursor contexts, target, busy, run; `commentPickerTitle` enables the Overview target picker, which checks busy before opening and resumes the same dispatcher after selection; a new workspace action is a new entry, not a new `case`. The dashboard and the diff pane (`diffBindings.actions()`) have their own `actions`. All names and command names share one namespace per view, and `keys.CheckActions` checks them. Each package's tests fail on a binding without a name.

## Rendering tests

- **Golden files** via `internal/golden`: compare `Render(w, h)` output at a fixed size against `testdata/*.golden`. Regenerate with `make golden` (`UPDATE_GOLDEN=1 go test ./...`) and **read the `.golden` diff before committing**. Whole-screen goldens always strip ANSI codes (`x/ansi`). A test about styling (focus borders, selection, colours) asserts specific elements against strings produced by the theme's own styles (for example `th.PaneBorderFocus.Render("╭")`) and never stores escape codes in a golden, so a palette change cannot break it.
- **Deterministic rendering**: tests must not depend on the terminal. Use a fixed theme and fixed Glamour style (never auto-detected light/dark), fixed widths, and an injected clock for relative times.
- Cover each view's main states: loading, empty, error, populated, and narrow widths.

## Theming

Colour flows through three layers, each built only from the one below (details in the `internal/userinterface/theme` package doc):

1. **Palette**: the 24 Base24 slots plus a light/dark variant (`theme/palette.go`; built-ins in `theme/palettes.go`). The only place colour values exist. The slots are unexported; only `roles.go` reads them.
2. **Roles**: what strig means by a colour (`text`, `muted`, `accent`, `added`, diff tints, syntax tokens, …), derived from slots in `theme/roles.go`. A theme may override any role with an exact colour; overrides are used as written, and only derived roles go through the contrast guard (a failing override is logged).
3. **Styles**: the named Lip Gloss styles on `theme.Theme`, built from roles only. Markdown (Glamour) styles are generated from the same roles. Code has one Chroma style per theme (`Theme.Syntax`): generated from the syntax roles through one token-to-role mapping (`theme.ClassOf`), or a bundled Chroma style the theme names with `syntax:`. The diff pane and Markdown code blocks both draw from it, per token type.

What `theme/enforce_test.go` checks (over every non-test file in `internal/userinterface`, with the rules proven on snippets):

- no `#rgb`/`#rrggbb`/`#rrggbbaa` string literal, `lipgloss.Color`/`ANSIColor`, `ansi.IndexedColor`, or `color.RGBA`-style literal outside the palette files;
- no named colour constants (`lipgloss.Red`, `color.Black`, …);
- no palette slot (`Base0x`, `.Slot`, `.colors`) outside `roles.go` and the palette files.

Rules for you:

- A new UI element uses an existing role. If none fits, add a role with a default derivation from slots (and a line in the role table in `docs/themes.md`).
- Never add palette slots, ANSI indices or raw colours to styles, views or components.
- Caches of rendered output (markdown, highlighting) include `Theme.Identifier` (a fingerprint of the final roles and the syntax style), or hold theme-independent data (token types).
- Chroma's style registry is a global map read by Glamour without a lock. Register styles (`ChromaStyleName`) and run Glamour only on the UI goroutine, never in a `tea.Cmd`.
- Tests that render Markdown or register Chroma styles don't use `test.Parallel` (the registry is unlocked; see the line above).
- Bubbles widgets that ship default styles (`textinput`, `help`, `list`, …) get their styles set from the theme. Never keep `DefaultStyles()` or `DefaultDarkStyles()`; the AST check can't see those.
